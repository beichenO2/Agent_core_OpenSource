# 置信度标注规范（Confidence Annotation Spec）

> 版本 1.0 | 2026-05-18
> 前置：P28 P-REFLEX（ADVANCED.md）
> 本文定义 Agent 报告中置信度标注的标准化体系

---

## 1. 三级置信度

| 等级 | 标签 | 含义 | 适用场景 | 渲染样式建议 |
|------|------|------|----------|-------------|
| L1 | `[确定]` | 直接从代码/SSoT/运行时输出读取，可立即复现验证 | 文件存在性、代码行内容、编译结果、测试输出 | 绿色标签 |
| L2 | `[高概率]` | 多个间接证据一致推出，但未直接执行验证步骤 | 功能推断、日志关联、文档与代码一致性 | 黄色标签 |
| L3 | `[推测]` | 基于训练知识、模式匹配或单一间接证据 | 历史行为推断、未读代码的结构猜测 | 红色/橙色标签 |

## 2. 标注位置

置信度标签**紧跟**在事实性断言之前：

```markdown
- [确定] SidebarProvider.ts 第 642 行存在 renderMarkdown 函数 [文件: src/sidebar/SidebarProvider.ts:642]
- [高概率] SSE 流式输出因 TS 编译错误未能打包 marked 库 [推理: TS 错误阻断 vite build → 产物缺失]
- [推测] 用户可能需要在 CI 中集成 compile-gate-check.sh [依据: 编译流程已有人工触发]
```

## 3. 强制标注场景

以下场景中，**每条事实性结论必须带置信度标签**：

| 场景 | 触发条件 |
|------|----------|
| 调研报告（格式 B） | `send_prompt` 包含"## 调研" |
| Bug 诊断 | 用户描述 bug 或 Agent 主动发现异常 |
| 自诊断 / 反身性报告 | 涉及 Agent 自身能力或状态的断言 |
| 项目状态汇报 | 涉及功能完成度、进度百分比 |
| 任务书编译 verify 阶段 | 编译门控中的代码验证步骤 |

## 4. 可选标注场景

以下场景可省略置信度标签（但鼓励标注）：

- 格式 A 任务完成汇报中的"改动摘要"（Agent 刚做完，天然 L1）
- 纯操作指令执行（"已运行 `npm install`"）
- 用户原文转述

## 5. 升级与降级

| 动作 | 条件 | 示例 |
|------|------|------|
| L3→L2 | 找到第二个独立证据 | 代码和文档同时指向某结论 |
| L2→L1 | 直接执行验证 | 运行测试并看到通过输出 |
| L1→L2 | 证据过期（文件被修改、版本变更） | 上次读取后 10+ 分钟且文件有改动 |
| L2→L3 | 发现矛盾证据 | SSoT 说 done 但代码未实现 |

## 6. 与 P28 的关系

- P28 §4 定义了三级置信度的语义
- 本文扩展了标注格式、强制场景、升降级规则
- P28 §1（断言必引证）+ 本文 = 完整的"证据+信心"双标注体系

## 7. 报告中的汇总

当一份报告包含 5+ 条断言时，在报告末尾附加置信度摘要：

```markdown
### 置信度统计
- [确定]: 8 条（67%）
- [高概率]: 3 条（25%）
- [推测]: 1 条（8%）
```

这帮助用户快速判断报告的整体可靠性。

## 8. 渲染建议（IDE / Hub Web）

| 标签 | 颜色 | 图标 |
|------|------|------|
| `[确定]` | `#4caf50`（绿） | ✓ |
| `[高概率]` | `#ff9800`（橙） | ~ |
| `[推测]` | `#f44336`（红） | ? |

前端渲染时，将 `[确定]`/`[高概率]`/`[推测]` 正则匹配并替换为对应颜色的行内标签。
