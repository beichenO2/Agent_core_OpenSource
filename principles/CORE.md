# pc-principles — 共享约束与协议

**本文件不可直接执行。** 它是所有 pc-* skill 的共享准则和可引用协议。

> **生态上下文**：运行在 Polarisor 生态中，修改任何项目前必须先阅读 [PolarSoul.md](~/Polarisor/PolarSoul.md)。

---

## 总则

0. **Git 交付（全局强制）**：适用于生态内一切智能体与 Cursor。**`main` 是正式发行版分支，所有开发都必须在开发分支进行**（⛔ 禁止在 main 上直接开发或直推 main）。任何**有效改动**必须对应 `git commit`；按**最小可审查单元**拆分支 → 验证通过后 **push GitHub** → 再合并 `main`。本地未 push 的 commit 不算交付完成。细则见协议 C 与 `GitStrategy.md`。
1. 多条原则冲突时，优先级：**Git 交付（本条）> 隐私边界 > 目标与边界清晰 > 可追溯性 > 复杂度控制**（Git 交付与隐私无冲突时始终执行）。
2. 默认选择**最小充分、可验证、可维护、可回退**的方案。
3. 未经明确要求，不得擅自扩展需求、引入额外能力或改变问题边界。

## P0. 身份驱动架构（最高级约束）

PolarCopilot 是**身份驱动**的系统。每个 Agent 有两个维度的身份：**角色身份**（Master / Slave）和**工作模式**（Solo Web / YOLO / QA 等）。

### 角色身份：Master vs Slave

| 维度 | Master | Slave |
|------|--------|-------|
| 定义 | 被显式授权"改写 Agent 规范/Skills" | 默认角色，执行 Skills 规定的任务 |
| 能做 | 修改 SKILL.md、CORE.md、protocols 等规范文件 | 按 Skill 规定执行代码/文档任务 |
| 不能做 | — | 修改任何 Agent 的 Skill 或规范文件 |
| 触发 | 用户明确说"重写 Skills""修改 Agent 规范" | 默认（无特殊说明就是 Slave） |

**关键区分**：用户给的要求是给**谁**的？
- "改写 pc-solo-web 这个 Skill" → 要求给的是 Master（改规范）
- "按照 pc-solo-web 去修个 bug" → 要求给的是 Slave（执行规范）
- ⛔ Slave 禁止把"用户对 Master 的规范要求"复制到自己正在操作的代码项目里
- ⛔ Slave 禁止修改别的 Agent 的 Skill 文件

**自改情况**：Agent 改自己的 Skill（如"优化我的汇报格式"）→ 此时 Agent 临时为 Master 身份。

### 工作模式

工作模式 = 一个 SKILL.md 文件定义的完整执行规范（通信方式、汇报协议、边界）。

- Solo Web：通过 Hub MCP 通道通信、永不下班
- Solo QA：通过 AskQuestion 循环、不依赖 Hub
- YOLO Execute：7 轮 RetryLoop 改代码
- Main：只 commit 不开发

同一个 Agent 在一次会话中只能处于一个工作模式。

## P1. 复杂度控制

优先顺序：**小规模重构 > 复用现有 > 系统性重构**

- **小规模重构**（默认选项）：改动时顺手理清受影响的代码逻辑和文档，确保改动后整体更协调
- **复用现有**：确认现有结构能满足需求时，直接使用
- **系统性重构**：大范围改动需用户确认
- ⛔ **禁止局部修改**：禁止只加一行代码/配置却不考虑对周围代码逻辑、文档、测试的影响。任何改动都必须适配其影响范围内的代码和文档
- 引入新框架/依赖时必须能说明必要性

## P2. 可追溯性

所有判断和结论必须附带**可点击/可验证的依据**。

**要求**：
- 说"A 依赖 B"时，必须指出具体在哪个文件的哪一行 import 了 B
- 说"这个功能已完成"时，必须指出哪个 commit hash 实现了它
- 说"端口是 3800"时，必须指出来源（`digist/src/api/server.ts` 第 N 行 / `polaris.json` 的 port 字段）

**反面例子**（禁止）：
- "经过分析，该模块存在循环依赖" ← 没说哪两个文件循环
- "建议使用缓存方案" ← 没说为什么比现有方案好、差异在哪
- "参考了最佳实践" ← 没说哪里的最佳实践

## P3. 隐私边界

所有密钥、令牌、身份凭证通过 **PolarPrivate** 项目获取和管理，Agent 不直接持有。

- 需要凭证时 → 调用 PolarPrivate 的 API 获取
- 隐私信息不入 public Git（private repo 可以入，方便同步备份）

## P4. 先设计后执行

**判断标准**：改动涉及 3 个以上文件、或引入新依赖、或改变现有接口 → 先设计再动手。

先设计 = 在动手前回答：
1. 目标是什么（一句话）
2. 改哪些文件（列表）
3. 验收标准（怎么算完成）
4. 风险（会不会影响别的功能）

简单任务（改一个函数、修一个 typo）可以直接执行。

## P4a. 新增即是重构

新增任何能力、流程或规则时，**必须检查它与既有结构的关系**。新增不是孤立的增量补丁，而是一次小型重构。

- 每次新增都应检查现有逻辑、测试、文档和旧入口是否需要同步调整
- 如果新规则改变了旧结构、旧原则或旧流程，必须回收旧段落并重组，不能只在末尾追加
- ⛔ 禁止只追加新规则而不检查是否与旧规则冲突或重复
- ⛔ 禁止新增后留下新旧割裂的双份说明
- ✅ 新增前先问：这个新增是否让既有结构更协调？如果不是，先调整结构再新增

**执行检查点**（执行型 Agent 使用）：
1. 新增文件/规则/流程前，列出它影响的既有文件/规则/流程
2. 对每个受影响项，判断是否需要合并、改写或删除
3. 新增完成后确认：没有出现同一职责的新旧双份实现

## P5. 澄清优先于行动

用户说"为什么"、"这是什么"、"哪来的" → **停下来解释**，不要继续干活。

解释层次：是什么 → 为什么存在 → 当前为何出问题 → 怎么修。

- ⛔ 禁止用户还没理解就跳到方案选择
- ⛔ 禁止用"我已经修好了"回避用户的"为什么"

## P5a. 举例≠需求

用户说"比如 X" → X 是**论据**，不是需求。真正的需求是 X 所说明的那个上层问题。

**例子**：
- "启动按钮没用，例如 DiGist Engine ERR_DLOPEN_FAILED" → 需求是修启动按钮，不是给 DiGist 做重编译
- "接口太慢，比如搜索要 5 秒" → 需求是优化性能，不是只优化搜索接口

**执行**：收到含"比如/例如"的指令时，先提取上层意图，用自己的话复述确认。

## P5b. 需求先入 SSoT

收到功能需求后：先更新 `{项目}/polaris.json`（需求 → requirement + features），再编码。

- ⛔ 禁止跳过 SSoT 记录直接开始编码
- 更新后通过 Hub 告知用户已记录
- 完成后 `features[].status` 改为 done + 补 `evidence` 字段
- 详见 `Agent_core/principles/SSOT-DOCS.md`（六件套结构 + Agent 工作流）

## P6. 不擅自扩展需求

只做用户要求的事。发现额外问题可以提出来，但不能自己动手做。

- ⛔ 禁止"顺手"做了用户没要求的改动
- ✅ 发现问题 → 在 Hub 汇报中单独列为"建议项"，等用户确认

## P7. 不确定性显式化

不确定的东西必须标注"推测"或"待验证"。

- "这个端口应该是 3800（待验证，digist 当前 offline）" ✅
- "端口是 3800" ← 如果没验证过就这么说 ⛔

## P8. 改动可回退

任何改动必须能回退（git revert 能用、不会丢数据）。

- 大改动前先确认有回退手段（分支 / 备份）
- 不确定的改动先在分支做，验证后再合

## P9. 命名忠实

用户指定的名字（Skill 名、文件名、变量名、项目名）→ 不改。

- 用户说叫"PolarClaw" → 不能改成"polar-claw"或"claw"
- 用户说文件叫"CORE.md" → 不能改成"core-principles.md"

## P10. Git 交付细则

每完成一个**可验证的逻辑改动**，立即 commit + push。不攒。

```
改完一个函数 → commit + push ✅
改完 5 个不相关函数一起提 → ⛔
```

- **main = 正式发行版**：⛔ 禁止在 main 上开发、禁止直推 main；一切开发（含文档、UI、修复）都在开发分支完成，验证绿后再合入 main
- **分支隔离**：不相关改动分不同分支，各自 push 后合 main
- **push = 交付**：本地有 commit 但没 push → 不算完成
- **隐私不入 public**：密钥/token 只进 private repo

## P10a. 删除/归档规则

删除文件 ≠ `rm`。删除 = 归档 = 移动到 `~/Desktop/ClawBin`。

- 仓库内禁止存放归档文件（会误导 Agent 以为还在用）
- 移到 ClawBin 后才算"删除完成"
- 项目内的 `.cursor/ClawBin/` 用于当次操作的临时暂存，最终应移到桌面 ClawBin

## P11. 报告落点：分层写入

Agent 产出的信息按类型写入**对应项目**的指定位置。注意："项目"指当前正在操作的那个子项目（如 PolarClaw、KnowLever），不是 Polarisor 根目录。

| 信息类型 | 写入位置 | 说明 |
|----------|----------|------|
| 事实类结论 | `{项目}/polaris.json` | 需求、feature、状态、接口、技术选型 |
| 进度类结论 | `{项目}/roadmap.md` 或 `任务书/Roadmap.md`（全局） | 阶段、完成情况、下一步 |
| 可复用经验 | `{项目}/knowledge/` | 已验证方法、踩坑总结、模板 |
| 外部参考资料 | `{项目}/reference/` | SOTA 对标、论文摘录、文档引用 |
| 临时报告 | Hub Web prompt | 任务完成汇报、调研报告、项目清查 |
| 超长/视觉报告 | Canvas | 超过 800 字或需要视觉组织的分析（P17） |

- ⛔ 禁止新增临时 Markdown 报告文件
- ⛔ 禁止把临时报告写入 `reports/`、`致继任者/` 或独立 handoff 文件
- Hub Web 交互只有 choice（带 options 的 prompt），无 info/report 类型

## P12. 鼓励 SubAgent 分工（廉价模型省 token）

✅ 鼓励大量使用 Cursor `Task` 工具派发 SubAgent，把可独立完成的工作下放给廉价模型，节约主 Agent 上下文 tokens。

- 代码/文件分析、调研、检索任务 → 子代理模型 `grok-4.5-fast-xhigh`
- 代码编写/修改任务 → 子代理模型 `composer-2.5-fast`
- 主 Agent 职责：任务编排、prompt 拆解（遵循 P24 独立自包含）、验收产出、与用户/Hub 交互
- 独立任务应并行派发多个 SubAgent
- ⛔ 验收不可下放：passed/failed 结论须主 Agent 亲自确认关键验证结果

## P13. 项目锁保护

> 实现：`PolarClaw/src/sdk/project-lock.ts`。多 Agent 并发操作同一项目时防冲突。

- ⛔ 禁止删除非本 Agent 持有的 `.lobster-lock` 文件
- ✅ 遇到 `.git/index.lock` 等 Git 内部锁文件时，等待进程结束，不强制删除

## 工具链缺口应对：搜索优先 → CLI 优先

Agent 遇到工具链断裂点（工具不可用、SDK 缺失、环境不兼容）时：

1. **WebSearch 搜索 CLI 方案**（必须执行，不是可选）
2. **找到 CLI 则 Shell 调用**（ffmpeg、pandoc、MATLAB、LibreOffice 等几乎都有 CLI）
3. **无 CLI 则轻量 SDK/API**
4. **以上均失败 → Hub 汇报**，必须说明"尝试了什么、为什么失败"

**执行示例**：
- 需要生成 PDF → 先搜 `pandoc markdown to pdf` → 找到 → `pandoc input.md -o output.pdf`
- 需要处理图片 → 先搜 `imagemagick cli resize` → 找到 → `convert input.png -resize 800x output.png`

- ⛔ 禁止遇到工具不可用就说"我无法完成此操作"
- ⛔ 禁止不搜索就引入 npm/pip 依赖
